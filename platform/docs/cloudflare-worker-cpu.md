# Cloudflare Free plan: Worker CPU limit and the INOK application (2026-11-16)

Worker `inok-app-staging` (Free plan, OpenNext + Next.js 16). Production Worker, production database and `inok.my` were not touched.

## Verified cause of error 1102 / HTTP 503
- Cloudflare's Limits page (updated 13 Nov 2026): Workers **Free = 10 ms CPU per request**, 128 MB memory per isolate, 1 s startup, 64 MiB uncompressed size, **no compressed size limit**. The 3 MiB figure in the earlier readiness report was wrong and is withdrawn; bundle size is not the cause (the staging bundle is 11.3 MB for the main handler, 40 MB in total, under 64 MiB).
- `wrangler tail` on the failing requests: `outcome: exceededCpu`, `cpuTime: 10`, `wallTime 12-16`, exception "Worker exceeded CPU time limit.", response 503 (shown to browsers as "error code: 1102"). Application errors were not involved.
- Enforcement is not a hard line: many requests that used 20-60 ms of CPU succeeded and others were cut at 10 ms, and the share cut changed with time and load (0 to 100 percent in different periods, same build). I cannot see Cloudflare's rule; I can only report what was measured.

## Failure rate under rapid sequential requests (40 per page, scoped build, no page cache)
`/api/v1/health` 0 of 40 failed; `/en/login` 19; `/en/terms` 17; `/en` 17; `/en/directory` 20. With the page cache on, the same eight public pages: 240 of 240 succeeded.

## What was changed (baseline commit `361729b`, live on staging as Worker version `3ef6e58a`)
1. **Scoped client messages.** The locale layout used to send the whole message catalogue (about 216 KB) to every page. Now it sends a small base set; each route area adds only what its client components use, and forms also get the keys that server actions answer with (`src/i18n/client-namespaces.ts` is generated by `scripts/client-namespaces.mjs` and checked by a unit test). This also made pages much smaller for visitors.
2. **Public-page cache** (`public-page-cache.mjs`, called from `cf-entry.mjs`). Anonymous GET requests for the legal pages, sign-in pages, home and directory are served from isolate memory. Never cached: any request with a query string, a Supabase session cookie, a Next RSC or action header, a non-GET method, or a response that is not a plain 200 HTML page. Every response gets a fresh CSP nonce (markup and header), so nonces are never shared. The `NEXT_LOCALE` cookie is still set. Covered by unit tests.
A first version of the legal-page cookie test failed on hosted because a stored copy lacked the locale cookie; that is fixed in the baseline.

## Technical constraint, stated plainly
A Next.js page rendered on Workers by OpenNext costs about **15 to 50 ms of CPU** (a bare route handler costs about 7 ms). Workers Free gives **10 ms per request**. Every uncached rendered request, including signed-in pages, server-action responses and RSC navigations, is therefore exposed to the limit, and a share of them fail with 503. Caching can protect the anonymous public pages (0-1 ms), but not signed-in or personalised pages. On the Free plan this application cannot be made reliable for signed-in use with the optimisations tried here.

## Recommended next action (needs your decision; nothing changed)
- Staging on Free is acceptable only as a demonstration that fails some clicks. For a real pilot, the Worker needs a higher CPU allowance; that is a plan change (Workers Paid sets a 30 s default CPU limit). I have not changed or proposed any plan beyond naming it, as you asked.
- If the plan must stay Free, the only remaining route is an architecture change (static pre-rendering plus browser-side data access to Supabase for signed-in screens). It is large and would need its own plan and tests; I did not start it.

## Update 2026-11-16 (branch `optimize/cf-free-render`): poisoned isolates, and what was changed on the branch

**New measured finding (wrangler tail, 12 sequential requests to `/en/terms`, build `e93ac199`).** Besides plain `exceededCpu` (503, error 1102), a second failure appears: a cold isolate whose module loading is cut off by the CPU limit stays alive in a broken state. Its log says `Error: Module 87429 was instantiated because it was required from module 55051, but the module factory is not available.` (earlier: `components.ComponentMod.handler is not a function`). Every later request that hits that isolate returns **HTTP 500 "Internal Server Error"** at 8-10 ms CPU, until the isolate is recycled. This explains failures that come in streaks (health 30 of 30 returned 500 right after one deployment, `/en/terms` 0 of 40, `/en/privacy` 0 of 40, while `/en/directory` served from the page cache gave 40 of 40) and why the same build passes three runs and then fails. My earlier statement in this session that the health 500s came from a "stale incremental build" is **withdrawn**: a clean rebuild coincided with the recovery, but the isolate explanation fits the evidence and the stale-build explanation was not proven.
Cause (inferred from the log, not from Cloudflare internals): the first request on a cold isolate instantiates the application's webpack modules (an 11 MB handler); that work alone approaches or passes 10 ms of CPU, and when the limit lands in the middle of it the module table is left half built.

**Changes on the branch** (staging only, Worker `e93ac199`):
1. Shared locale-aware `Link` has prefetch off by default (no background `?_rsc=` renders from visible links).
2. Signed-in render: the layout, the page gate and the profile/membership lookups now share one Auth-server check and one profile and membership query per render (React `cache`, per request). Before: about 3 identical `getUser` calls and 2 membership queries per signed-in page, plus the proxy's own check. Server actions and route handlers are unchanged.

**Hosted result on the branch build (no retries, one runner):** two full runs: 1 passed, 4 failed, 15 not run each time. The first failures were the legal pages and the public-pages check answering 503/500 (isolate failures above), then a login that returned the Next error page. These runs do not show the branch to be better or worse than the baseline; the dominant failure is cold-isolate loading, which none of the changes touch.

**Measured CPU of requests that succeeded (tail, branch build):** signed-in/admin pages 36-97 ms (median 54-69), router RSC fetches 16-100 ms, login page 0-21 ms (cached copy) with one 505 ms cold render. Enforcement is not a hard 10 ms: requests of 40-500 ms were served as `ok`; the cut-off is probabilistic.

**Not done, and why:**
- *Static pre-rendering of legal pages with Cloudflare asset delivery:* pages read the per-request CSP nonce, so they render dynamically by design; a static copy would need a hash-based script policy (a security change), and while the pre-launch access gate runs in the Worker every request invokes the Worker anyway. The in-memory page cache already serves those pages at 0-1 ms once an isolate is warm; it cannot help a cold or poisoned isolate.
- *Browser-side Supabase for signed-in screens:* not started. The application relies on server-side RPCs with limited direct grants, so this is a multi-week migration with a per-workflow authorisation review, and it would still leave every first request on a cold isolate exposed to the module-loading problem.
- Steps 8 (server-action/API tuning) and 12 (final acceptance) were not completed: no build on the Free plan produced a clean hosted run today.
