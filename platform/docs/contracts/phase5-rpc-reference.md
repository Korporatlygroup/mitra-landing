# Phase 5 RPC reference (database side)

Migrations `20260701000110`-`000114`. All functions are `security definer`, `search_path = ''`, called through PostgREST `rpc`. Errors are `PT401/403/404/409/422/429` with a message key (below). `uuid` ids; `version` numbers are optimistic locks. **Hidden resources are 404; naming an organisation you are not a member of is 403.** Partner write RPCs additionally need an `approved` `partner_profiles` row (409 `partner_not_approved`), and partner owners need MFA (`aal2`) like every partner owner (otherwise 403 `forbidden`). Writes that create user content call `require_consent` (403 `consent_required`).

## Permissions (new `role_permissions` rows, mirrored in `src/lib/permissions.ts`)
| Permission | Roles |
|---|---|
| `supplier:manage`, `catalogue:manage`, `sourcing:respond` | owner, manager, staff (viewer: read-only through `is_member`) |
| `supplier:review`, `catalogue:review`, `partner:manage` | admin_review, admin_super |
| `catalogue:moderate` | admin_support, admin_super |
`suspend_supplier`, `suspend_product`, `reinstate_product` accept `supplier:review`/`catalogue:review` **or** `catalogue:moderate`; `reinstate_supplier` needs `supplier:review`. `catalogue_stats` accepts `report:view`, `supplier:review`, `catalogue:review` or `catalogue:moderate`. Reviewers cannot decide on a partner they were ever a member of or provisioned (`403 conflict_of_interest`). Buyers: `request:post` in an org of type `buyer` or `business`.

## Storage
* Supplier evidence: existing private bucket `verification-docs`, path `supplier/<partner_org_uuid>/<supplier_uuid>/<file>` (`<file>` = `[A-Za-z0-9._-]{8,120}`), pdf/png/jpeg, 10 MiB.
* Product images: NEW private bucket `catalogue-media` (created in migration 111; 5 MiB; png/jpeg/webp), path `products/<partner_org_uuid>/<product_uuid>/<file>`. Max 8 images per product. No storage policy for any API role.
* Server code (service role) uploads/scans; browsers never touch storage. Clean-up of orphaned objects after an org is deleted is not done in SQL.

## Service-role functions (upload pipeline, same pattern as Phase 2)
* `service_register_supplier_document(p_org, p_user, p_supplier, p_doc_type text, p_display_name, p_mime, p_size bigint, p_sha256, p_storage_path, p_scan_status scan_status, p_scan_engine) -> uuid`. `doc_type` in `business_registration|tax_registration|export_licence|trade_reference|catalogue|other`. Max 20 per supplier.
* `service_set_supplier_document_scan(p_doc, p_status, p_engine) -> void` (409 `already_scanned` unless pending/failed, or clean->infected).
* `service_list_unscanned_supplier_documents(p_limit) -> table(id, storage_path, mime_type)`.
* `service_register_product_media(p_org, p_user, p_product, p_mime, p_size bigint, p_sha256, p_storage_path, p_scan_status, p_scan_engine, p_alt) -> uuid`; `service_set_product_media_scan(p_media, p_status, p_engine)`; `service_list_unscanned_product_media(p_limit)`.
* Infected files are never registered (422 `infected_not_stored`). Unscanned/failed files are never served.

## Partner organisations
* `save_partner_profile(p_org, p_display_name, p_contact_email) -> {org_id, status, created}` (needs `org:manage`; creates the `pending` profile of a self-created partner org). Notifies admins `partner.submitted`.
* `approve_partner(p_org, p_reason) -> void` (also reinstates); `suspend_partner(p_org, p_reason>=5 chars) -> void`. `partner:manage`. Notifies owners `partner.decided`.
* `provision_partner(p_name, p_owner_email, p_display_name) -> {org_id, invitation_id, token}`: admin creates an **approved** partner org (no admin membership) and an owner invitation (7 days). The server mails the token. `resend_partner_invitation(p_org, p_owner_email) -> {org_id, invitation_id, token}` while the org has no active owner.
* `accept_partner_invitation(p_token) -> {org_id, role:'owner'}` or `{code:'PT404', message:'invalid_invitation'}` with HTTP status set to 404 (same non-raising pattern as `accept_invitation`). **The generic `accept_invitation` refuses these invitations** (its inviter must be a member); owners accept through this function. Owner still needs MFA for every action.
* `list_partner_orgs(p_status default null, p_offset default 0) -> {offset,total,items:[{org_id,name,display_name,status,provisioned,created_at,decided_at,decision_reason,conflict_of_interest}]}`.
* Status machine `partner_status`: `pending -> approved <-> suspended`.

## Suppliers
Status `supplier_status`: `draft -> awaiting_review -> approved | rejected | more_info_needed`; `rejected|more_info_needed -> draft` on edit; `approved <-> suspended`. An **approved** supplier stays approved/live while a revised draft is under review: `draft_submitted_version` is set during any review; a rejected/more-info decision on a revision leaves the supplier `approved` with `decision_reason`.
* `save_supplier_draft(p_org, p_supplier null=create, p_data, p_expected_version) -> {id, code, version, status}`. Keys: `name,country,state_city,main_category(slug),description(>=20 to submit),capabilities[<=10],code(create only)` and private `contact_name,contact_email,contact_phone,registration_id,website`. `p_expected_version` = `draft_version` (ignored on create).
* `submit_supplier(p_org, p_supplier, p_expected_version) -> void` (needs contact name + email or phone, and >=1 clean document; locks submitted documents). `withdraw_supplier_submission(p_org, p_supplier)`.
* `review_supplier(p_supplier, p_decision approve|reject|request_info, p_reason, p_checks text[], p_expected_version)`: `p_expected_version` = `draft_submitted_version`. Reason >=5 chars for reject/request_info. Approve needs 1-6 distinct checks from `contact_reachable, registration_document_seen, address_consistent, catalogue_consistent, trade_reference, identity_document_seen`.
* `suspend_supplier(p_supplier, p_reason)`, `reinstate_supplier(p_supplier, p_reason)`.
* `list_my_suppliers(p_org) -> {items:[summary]}`; `get_supplier(p_supplier) -> summary + {draft, live{...}, private{contact...}, suspended_reason, documents[], events[]}` (partner members, and reviewers for non-draft). Summary: `{id,partner_org_id,code,status,name,country,draft_version,draft_submitted_version,live_draft_version,has_unsubmitted_changes,version,reviewed_at,review_checks,decision_reason,submitted_at,updated_at}`.
* `get_supplier_document_access(p_doc) -> {storage_path,mime_type,display_name}` (audited; clean only; partner `supplier:manage` or reviewer for locked docs). `remove_supplier_document(p_doc) -> storage_path` (409 `document_in_use` when locked).
* Public verification wording comes from `review_checks` + `reviewed_at` only ("MITRA reviewed ... on <date>"). Never "trusted"/"verified with an authority".

## Products
Status `product_status`: `draft -> submitted -> approved | changes_requested | rejected`; `approved -> published <-> unpublished`; any non-draft `-> suspended` (reinstate returns `unpublished`, or the earlier non-published state). Revisions (`product_revisions`) are immutable and have their own status `submitted|changes_requested|approved|rejected|published|superseded`. For an already published/unpublished product, editing and review happen on a pending revision while `products.status` stays `published/unpublished` and the live copy is untouched until `publish_product`.
Version rule: `save_product_draft` and `submit_product` take `draft_version`; `review_product` and `publish_product` take `products.version` (both returned by `list_my_products`/`get_my_product`).
* `save_product_draft(p_org, p_supplier, p_product null=create, p_data, p_expected_version) -> {id, sku, version, draft_version, status}`. Create needs `p_data.sku`; SKU is immutable and unique per supplier case-insensitively (409 `sku_exists`). Merge semantics: null or empty string removes a key; `tiers`, `variants`, `specs` replace wholesale.
* `submit_product(p_org, p_product, p_expected_version) -> {id, revision_id, rev_no, created}` (strict validation; first error key is the 422 message; supplier must be approved).
* `publish_product(p_org, p_product, p_expected_version) -> void` (approved revision, or re-publish of an unpublished one; supplier must be approved). `unpublish_product(p_org, p_product)`.
* `review_product(p_product, p_decision approve|reject|request_changes, p_reason, p_expected_version)`; `suspend_product(p_product, p_reason)`; `reinstate_product(p_product, p_reason)`.
* `list_my_products(p_org, p_supplier null, p_status null, p_offset 0, p_limit 25) -> {total,limit,offset,items:[summary]}`; `get_my_product(p_org, p_product) -> summary + {draft, suspended_reason, revisions[], media[]}`. Summary: `{id,supplier_id,sku,status,name,version,draft_version,live_revision_id,pending_revision{id,rev_no,status,reason,decided_at},has_unsubmitted_changes,published_at,updated_at}`.
* Media: `update_product_media(p_media, p_alt, p_sort)`, `remove_product_media(p_media) -> storage_path`, `get_product_media_access(p_media) -> {storage_path,mime_type}` (granted to anon too: public only for approved clean images of visible products; partner members and reviewers can open unapproved clean ones). Images become public only if they were part of the approved revision.

### Product data (draft / import row shape)
Keys (flat): `sku,name,description,category_slug,unit,moq,currency(INR|MYR|USD),price_mode(tiers|fixed|request),unit_price,tiers[{min_qty,max_qty|null,unit_price,variant_sku?}],variants[{sku,label,attributes{},moq?}],lead_time_min_days,lead_time_max_days,availability_status(available|made_to_order|limited|unavailable),availability_confirmed_on,price_confirmed_on,specs{},packaging`. Money: string or JSON number, at most 2 decimals, > 0. Quantities in tiers are whole numbers >= 1; tiers per (product, variant) must be listed ascending, **contiguous (gaps refused)**, non-overlapping, and the last one open-ended; first tier must start at or below the MOQ (strict). Dates `YYYY-MM-DD`, not in the future. Text starting with `= + - @` or tab/CR is refused (`formula_text`). Limits: name 160, description 2000, packaging 300, unit 30, 20 specs, 50 variants, 60 tiers.
Validator error keys (`private.validate_product_data`) may carry a detail after `:` (a field name, or a 1-based index): `unknown_field:<key>`, `formula_text:<field>`, `too_long:<field>`, `invalid_text:<field>`, `invalid_date:<field>`, `future_date:<field>`, `invalid_lead_time[:<field>]`, `invalid_variant:<n>`, `invalid_variant_sku:<n>`, `duplicate_variant_sku:<n>`, `invalid_variant_moq:<n>`, `invalid_tier:<n>`, `invalid_tier_qty:<n>`, `invalid_price:tiers[<n>]`, `tier_unknown_variant:<n>`. Plain keys: `invalid_data, invalid_<scalar field>, name_required, unit_required, category_required, moq_required, price_mode_required, availability_required, availability_date_required, price_date_required, currency_required, price_required, tiers_required, tiers_not_allowed, unit_price_not_allowed, price_not_allowed, invalid_name, invalid_sku, invalid_category, invalid_moq, invalid_currency, invalid_price, invalid_price_mode, invalid_availability, invalid_spec, too_many_specs, too_many_variants, too_many_tiers, tier_not_ascending, tier_overlap, tier_gap, tier_last_not_open, tier_does_not_cover_moq`. The client should map by the part before the first `:`.

## Import
* `stage_import(p_partner_org, p_supplier, p_mode create_only|create_or_update, p_file_name, p_sha256, p_rows jsonb[]) -> {job_id, created, status previewed|failed|committed, counts{total,valid,invalid,duplicate}, rows[problem rows: {row_no,sku,status,action,errors[],name}]}`. 1-2000 rows, 8 MB. Row = flat product data plus `_row` (spreadsheet row number, unique positive int, default = position) and optional `_client_invalid` (array of strings; non-empty marks the row invalid with `client_validation_failed`). Rows must name no supplier or organisation (`unknown_field:supplier_id` etc.). Idempotent per `(partner, supplier, sha256, mode)`: a retry returns the same job (previewed/committed); failed/cancelled jobs are re-staged. Zero valid rows -> status `failed`. **Duplicate SKUs: only later copies are `duplicate`** (`duplicate_sku_in_file`), the first copy keeps its own status (same rule as `src/server/import`). Row statuses `valid|invalid|duplicate`; errors may be `sku_exists`, `product_suspended`, `product_under_review`, `<field>_required`, validator keys.
* `commit_import(p_job, p_confirm_overwrite boolean) -> {job_id, status:'committed', created, updated, skipped, repeat}`. Re-validates every row. Writes **drafts only** (never publishes). `create_or_update` requires `p_confirm_overwrite = true` (422 `overwrite_confirmation_required`); updates merge into the existing draft (switching price mode drops the other mode's fields). Missing `price_confirmed_on` / `availability_confirmed_on` default to the commit date. Audit `catalogue.import_committed` lists SKUs created/updated.
* `cancel_import(p_job)`, `list_imports(p_org, p_supplier null, p_offset 0) -> {offset, items:[{id,supplier_id,mode,status,file_name,counts,created_at,committed_at}]}`, `get_import(p_org, p_job, p_kind problems|valid|all, p_offset) -> job + {rows[]}` (100 per page).

## Public catalogue and buyers (search/detail/compare are also granted to `anon`)
Visible = `products.status='published'` AND supplier `approved` AND partner profile `approved` AND partner org active.
* `search_catalogue(p_q, p_category, p_supplier, p_moq_max, p_price_min, p_price_max, p_currency, p_offset 0, p_limit 20 (max 50)) -> {total,limit,offset,items[],categories[slugs]}`. `p_q` max 80 chars (name, description, SKU, supplier name, full text). Price filters need `p_currency` (422 `currency_required`) and compare against `from_price` (lowest tier or fixed price). Order: SKU match, name, supplier name, newest, id (stable).
* Item (list): `{id,sku,name,category_slug,unit,moq,currency,price_mode,from_price,price_confirmed_on,lead_time_min_days,lead_time_max_days,availability_status,availability_confirmed_on,availability_outdated(>90 days),published_at,summary,image_id,supplier{id,name,country,state_city,reviewed{checks[],reviewed_at}}}`. Detail adds `description,specs,packaging,variants[{id,sku,label,attributes,moq}],tiers[{variant_sku,min_qty,max_qty,unit_price,currency}],media[{id,alt}],supplier_detail{description,capabilities,main_category}`. No supplier contact, evidence, or partner org is ever included.
* `get_catalogue_item(p_id)` (404 if not visible); `compare_items(p_ids uuid[<=4]) -> {items[detail], unavailable[ids]}`.
* `save_product(p_product) -> {product_id,saved,created}`; `unsave_product(p_product)`; `list_saved_products(p_offset) -> {offset,total,items:[{product_id,saved_at,available:true,item}|{product_id,saved_at,available:false,name,supplier_name}]}`. Unpublished products stay in the list with the name saved at the time.
* `report_product(p_product, p_reason misleading|counterfeit|prohibited|wrong_price|offensive|spam|other, p_note) -> {id}` (404 unless published; 409 `already_reported`; 10/day).

## Sourcing requests
Status `submitted -> acknowledged | clarification_requested`; `clarification_requested -> submitted` when the buyer replies (**contract change**: the reply reopens it for the partner); `submitted|acknowledged|clarification_requested -> closed` (partner) or `withdrawn` (buyer). Ref `SR-` + 8 chars of `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`.
* `submit_sourcing_request(p_buyer_org, p_key (8-80 chars), p_items [{product_id, variant_sku?, quantity}] (1-20, one supplier), p_destination_state (Malaysian state), p_destination_city, p_needed_by date, p_notes) -> {id, reference, status, created}`. Same key + same payload returns the same request (`created:false`); same key, different payload 409 `idempotency_key_reused`. Quantity below the (variant) MOQ 422 `below_moq`. Each line stores a **snapshot** (name, sku, unit, moq, currency, price mode, tiers shown, `applicable_unit_price` for the quantity, confirmed dates, variant, supplier name). Supplier/partner not approved: 409 `supplier_not_available`; unpublished product: 404.
* `list_my_sourcing_requests(p_buyer_org, p_offset)`, `list_partner_requests(p_org, p_status, p_offset) -> {offset,total,items:[{id,reference,status,supplier_name,destination_state,needed_by,version,item_count,buyer_name (partner side only),created_at,updated_at}]}`, `get_sourcing_request(p_request) -> summary + {your_side buyer|partner, buyer_org_id (buyer), partner_org_id (partner), supplier_id, destination_city, notes, first_response_at, items[{line_no,product_id,variant_id,quantity,unit,snapshot,still_available}], events[{kind,note,at,by}]}`.
* `respond_sourcing_request(p_request, p_action acknowledge|clarify, p_note (>=5 chars for clarify), p_expected_version null) -> {id,status,version}` (partner `sourcing:respond`, partner and supplier approved); `reply_sourcing_request(p_request, p_note)`; `withdraw_sourcing_request(p_request)`; `close_sourcing_request(p_request, p_note)`.

## Concurrency (lock order)
Always supplier row (FOR SHARE for product/import/sourcing writes, FOR UPDATE for supplier review/suspension/evidence), then job (imports), then product rows (ordered by SKU), then revisions; sourcing requests lock supplier then request; events are append-only. No function takes a product lock before its supplier lock.

## Erasure
Every foreign key to `organisations`, `auth.users` and Phase 3/4 tables has an explicit `on delete`: owned rows cascade; authorship columns are `set null`; `sourcing_requests.partner_org_id/supplier_id` are `set null` (the buyer keeps history and the supplier name); `supplier_events` has no foreign key (append-only history survives). Stored files are not deleted by SQL.
